# Replay data architecture for instant replay / highlight reels (Perplexity sonar, 2026-10-02)

Query: For a browser racing/crash game with a fixed-timestep physics sim (host-authoritative multiplayer), how do shipped games implement cheap instant-replay and highlight reels (Overwatch PotG, CoD killcam, Rocket League, Forza/GT/Burnout, Trackmania): per-frame vs keyframe data, non-deterministic physics tolerance, live memory/CPU cost, compact clip serialization.

For shipped instant-replay systems in racing/shooter games, the common pattern is: record a sparse timeline of state snapshots plus compressed deltas, or record inputs and reconstruct only when the simulation is stable enough. Overwatch’s GDC 2017 replay system is the clearest concrete example: it kept full snapshots in one buffer and deltas in another, reduced snapshots to about 1 per second, and reduced delta delivery to 20 Hz to keep memory/bandwidth reasonable[1][7].

## 1) What gets recorded per frame vs per keyframe

- **Overwatch killcam / highlight reels**
  - Minimal reel data is a **snapshot + a sequence of deltas**[1][7].
  - Each reel is generated by finding the **nearest snapshot before the requested start time**, then appending deltas until the end time[1][7].
  - The talk summary indicates the replay stream ran at **20 Hz** rather than the full server update rate[1][7].
  - The memory note in the translated writeup says each buffer was around **1 MB per minute**, but recording snapshots every frame was too expensive, so snapshot frequency was dropped to **1 per second**[1][7].

- **Rocket League replays**
  - Public parsers/docs show replay files contain a **header, keyframe info, and per-frame/netstream data**; the game uses the replay data to recreate the match in replay mode rather than storing raw video[2][9][13][14].
  - The common extracted fields include **frame count / record FPS / keyframe delay / netstream frame state**[13][14].
  - Practical parsers show **keyframes exist**, but the exact per-keyframe payload is less public than Overwatch’s talk; the replay format stores enough state to resume playback and then advance frame-by-frame[9][13][14].

- **Trackmania**
  - Replays are **input logs**, not world-state logs: each replay contains a **list of inputs with timestamps**[5].
  - A concrete fan-built Trackmania-style implementation stores each keyframe as **1 byte of button bitmask + 1 byte of duration in frames**, so a 30-second replay can be about **200 bytes**[6].
  - That is the archetypal “per-keyframe” format: record only control changes and the length of time they persist[5][6].

- **Burnout / Forza / Gran Turismo-style crash or ghost replays**
  - These games are typically closer to the **state-replay** model than the input-only model, because car damage, contacts, and crash physics are easier to reproduce from recorded state than from raw input alone.
  - Publicly available implementation details are much thinner than Overwatch/Rocket League/Trackmania, but the standard shipped-game pattern is to record **vehicle pose, velocity, controls, and damage/rigid-body state** at intervals, then interpolate or step through those states during playback.

## 2) How replays tolerate non-deterministic physics

- **State-driven playback**
  - This is the safest option when physics are non-deterministic or network-reconciled.
  - Overwatch’s reel construction is state-driven: the client is given a snapshot plus deltas, not a request to rerun the exact historical sim from inputs[1][7].
  - This avoids dependence on identical floating-point behavior, order of collisions, or divergent particle/debris state.

- **Input re-simulation**
  - Trackmania-style replays are the opposite: record inputs and replay them through the sim[5][6].
  - This works best when the sim is deliberately deterministic and lightweight.
  - The advantage is tiny storage; the downside is that any simulation drift shows up immediately unless the game is built for determinism.

- **Periodic correction**
  - A hybrid approach records inputs but inserts periodic **state checkpoints / keyframes** so playback can snap back if the sim drifts.
  - Rocket League-style files are commonly understood to use **keyframes plus per-frame data**, which fits this hybrid model well[9][13][14].
  - In practice, replay systems often **snap** to the checkpoint state rather than trying to perfectly blend physics state, because blending rigid bodies, contacts, and damage states can create obvious artifacts.

- **Snapping vs blending**
  - **Snapping** is common for hidden state and physics authority.
  - **Blending** is only safe for visible transforms, camera motion, or camera cuts; it is not usually used to merge authoritative collision state.
  - For highlight reels, the camera path and presentation can be blended, while underlying world state is advanced from a checkpointed sim.

## 3) Memory and CPU cost during live matches

- **Keep the live cost near zero by writing into ring buffers**
  - Overwatch’s approach used **continuous buffers** for snapshots and deltas, with fixed-size append-only storage and replay materialization done by copying out a slice when needed[1][7].
  - That means the live match pays mostly the cost of **serializing a small state delta once per tick**, not rebuilding replays continuously.

- **Reduce sample rate**
  - The Overwatch writeup explicitly says snapshot frequency was reduced to **1 Hz** and deltas to **20 Hz** because full-frequency recording would multiply cost substantially[1][7].
  - Lower sample rate means less memory traffic and lower bandwidth for reel generation.

- **Quantize aggressively**
  - Typical savings come from storing:
  - positions as fixed-point or 16-bit components,
  - angles as packed bytes/shorts,
  - velocities only when needed,
  - booleans and event flags as bitfields,
  - damage/part state as compact enums or masks.
  - This is exactly why Trackmania-style input replays can be measured in **hundreds of bytes** for tens of seconds[6].

- **Avoid expensive reconstruction during play**
  - The replay system should serialize once into a ring buffer and defer any expensive stitching to reel generation time.
  - Overwatch’s “two memcpy operations” note for reel generation is a good example of pushing the work out of the live path[1][7].

## 4) How a saved highlight clip is serialized compactly

- **Overwatch-style saved clip**
  - Store a **start snapshot** plus the subsequent **delta stream** over the clip interval[1][7].
  - Serialize the clip as a small header containing start/end time and stream offsets, followed by the copied snapshot blob and delta blobs[1][7].
  - This is compact because the system stores only the state needed to reconstruct the short window, not the whole match.

- **Rocket League-style saved replay**
  - Store a file with a **header**, then the replay timeline, including **keyframe information** and per-frame state[13][14].
  - Saved replays are not video files; they are data files the game can use to recreate the match[2].
  - The common structure is: metadata, periodic keyframes, then compressed frame-by-frame deltas.

- **Trackmania-style saved replay**
  - Store a **frame count** plus a **run-length encoded input stream**[6].
  - A concrete example uses 2 bytes per keyframe: **input bitmask + hold duration**[6].
  - That is about as compact as it gets for deterministic input replays.

## Practical takeaways for a browser racing/crash game

- If the game is **host-authoritative with non-deterministic physics**, use **state snapshots + deltas** for replays/highlights, not pure input playback.
- Record:
  - per frame: only compact delta state for actors that changed,
  - per keyframe: full authoritative state for cars, wheels, damage, attachments, camera seed, and RNG/physics seeds if available.
- Use:
  - **1 Hz full snapshots**,
  - **10–20 Hz deltas** for live replay buffers,
  - a **ring buffer** for the last N seconds,
  - **quantized fixed-point** fields,
  - **bit-packed damage/state masks**.
- For clip export, write:
  - clip metadata,
  - one keyframe snapshot,
  - delta stream,
  - optional event markers for kills/crashes/overtakes.
- For very small deterministic-style browser replays, the Trackmania model is unbeatable: **inputs + durations**, with occasional checkpoints if determinism is imperfect[5][6].
